# QR Transfer V2 完整修复设计

## 目标

在保持发送端和接收端各自为单个、自包含 HTML 文件的前提下，重构文本与文件传输协议，完整修复以下问题：

- 文件数据片早于元数据片到达时，已接收数据被清空。
- 扫描另一文件时，界面状态与持久化会话元数据发生错配。
- 恢复横幅把不可信文件名拼入 `innerHTML`，形成存储型 HTML/脚本注入。
- 现有测试复制生产逻辑且固定先接收元数据，无法捕获真实接收端的乱序与会话问题。

旧版私有文本和文件 QR 协议不需要兼容。公有文本 QR 继续保持普通扫描器可读。

## 产品模式

发送端把数据类型和协议模式明确分成三条路径：

| 数据类型 | 模式 | QR 载荷 | 接收方式 |
|---|---|---|---|
| 文本 | 公有 | 原始 UTF-8 明文；多片时仅增加人类可读序号 | 任意二维码扫描器逐片读取 |
| 文本 | 私有 | V2 紧凑分片协议 | 本项目接收端连续扫描、自动去重和拼接 |
| 文件 | 私有 | V2 紧凑文件分片协议 | 本项目接收端连续扫描、校验并下载 |

文件模式不提供公有协议。公有文本模式不承诺第三方扫描器自动拼接，只保证每张 QR 都能作为普通明文 QR 被独立识别。

## 自包含约束

- `sender.html` 内嵌 QR 生成库、SHA-256 调用封装、V2 编码、分片、补传和全部 UI 逻辑。
- `receiver.html` 内嵌 QR 扫描库、V2 验证、状态管理、持久化、拼接、校验和全部 UI 逻辑。
- 两个页面均不得增加 CDN、外部 JavaScript、ES Module 导入、服务端接口或构建时依赖。
- 单独复制并离线打开任一页面时，其自身功能必须可用。
- `test.html` 是开发验证页面，不是发送端或接收端的运行时依赖。

## 公有文本协议

### 单片文本

能够装入一个 QR 时，载荷就是用户输入的原始 UTF-8 文本，不附加 JSON、Base64、协议版本或私有标记。普通相机和任意二维码扫描器应直接显示原文。

### 多片文本

超过单个 QR 容量时，按 UTF-8 字节边界拆分，禁止切断 Unicode 码点。每片使用以下明文格式：

```text
【QR文本 2/5】
本片原始文本……
```

序号从 1 开始。前缀必须参与容量计算；每片仍是标准明文 QR，不要求第三方扫描器理解协议。

## 私有 V2 协议

### 通用信封

私有文本和文件统一采用紧凑 JSON 信封：

```json
{"v":2,"k":"f","x":"6db0c792d8f41a30","i":3,"t":42,"d":"..."}
```

字段定义：

- `v`：协议版本，固定为整数 `2`。
- `k`：数据类型，`t` 表示文本，`f` 表示文件。
- `x`：传输 ID，固定 16 个小写十六进制字符。
- `i`：从 0 开始的片号。
- `t`：总片数，包含元数据片。
- `d`：本片 Base64 数据；元数据片可为空字符串。
- `m`：仅元数据片允许出现的元数据对象。

所有私有文本和文件传输均使用片号 0 作为元数据片，片号 1 至 `t - 1` 承载数据。统一采用 0-based 内部协议，UI 和补传编号继续显示 1-based 编号。

### 传输 ID 与完整性

- 文件内容使用 Web Crypto 计算完整 SHA-256，保存为 64 位十六进制字符串 `h`。
- 文件传输 ID 由 `文件名 + NUL + 文件大小 + NUL + 完整 SHA-256` 再做 SHA-256，并取前 16 个十六进制字符，确保同内容不同文件名不会共用活动会话。
- 私有文本对完整 UTF-8 字节计算 SHA-256，并取前 16 个十六进制字符作为传输 ID；完整摘要保存在元数据中。
- 传输 ID 用于路由片段，完整 SHA-256 用于最终字节完整性校验，两者用途不得混用。

### 元数据

私有文本元数据：

```json
{"m":{"h":"<64 hex>","e":"utf8"}}
```

文件元数据：

```json
{"m":{"n":"report.pdf","y":"application/pdf","s":12345,"h":"<64 hex>"}}
```

其中 `n` 是文件名，`y` 是 MIME 类型，`s` 是原始字节数，`h` 是原始内容 SHA-256。

### QR 标准兼容性

- 每一片都编码为普通 QR Code 文本载荷，不使用自定义图像格式、彩色通道或非标准二维码扩展。
- 私有 QR 可被第三方扫描器识别为 JSON 文本，但自动拼接仅由本项目接收端支持。
- 公有文本 QR 必须保持原始明文语义，不得复用私有 V2 信封。

## 发送端数据流

### 公有文本

1. 把输入按 UTF-8 编码。
2. 根据当前纠错级别和序号前缀计算单片容量。
3. 单片时直接编码原文；多片时按 Unicode 码点安全拆分并加可读序号。
4. 使用现有标准 QR 生成器显示、循环和单片浏览。

### 私有文本

1. 把完整文本编码为 UTF-8 字节并计算 SHA-256。
2. 生成稳定传输 ID。
3. 生成元数据片和 Base64 数据片。
4. 生成全部 QR，并保留现有循环、单片跳转和指定编号补传能力。

### 私有文件

1. 使用 `FileReader.readAsArrayBuffer` 读取原始文件字节。
2. 计算原始字节 SHA-256 和稳定传输 ID。
3. 把原始字节转换为 Base64，并根据当前纠错级别拆片。
4. 生成元数据片和数据片。
5. 生成全部 QR；任一片编码失败时，整体生成必须进入失败状态，不得把失败占位片当作可发送片继续播放。

分片容量必须按 V2 JSON 的实际 UTF-8 字节数校验，不能只依赖固定的估算开销。生成时选择能够装入目标 QR 版本的最大安全数据长度。

## 接收端状态机

接收端同时只维护一个活动私有传输：

```text
空闲 → 已识别传输（元数据可缺失） → 接收中 → 校验中 → 完成/损坏
```

### 接受规则

1. 收到 V2 片段后，先完整验证信封；验证失败的片段不进入状态和持久化。
2. 空闲状态收到任意合法私有片段时，按 `x + k + t` 创建活动会话。即使先收到数据片，也必须立即保存。
3. 活动传输收到相同 `x + k + t` 的片段时合并；重复片只更新“重复”提示，不重复计数。
4. 活动传输收到不同传输 ID、类型或总片数的数据片时忽略，并显示“检测到其他传输，当前传输未切换”。
5. 活动传输期间不会由外来元数据片静默切换文件。用户必须使用现有“重新开始”操作清空当前会话后才能接收新传输。
6. 元数据片到达时只附加到同一活动会话，不清空任何已收到数据片。

### 完成条件

只有同时满足以下条件才进入完成状态：

- 元数据片存在且通过字段验证。
- `0...t-1` 每个片号都恰好存在。
- 拼接后的 Base64 可解码。
- 解码后的字节数与文件元数据 `s` 一致；文本按 UTF-8 成功解码。
- 完整内容 SHA-256 与元数据 `h` 一致。

校验失败时进入“损坏”状态，停止自动完成并保持补传/重新开始入口；下载按钮必须禁用。

## 持久化与恢复

V2 会话保存以下字段：版本、类型、传输 ID、总片数、片段表、可空元数据、创建时间和最后更新时间。

- 任意首个合法片段都创建并保存会话，不再要求元数据先到。
- 恢复无元数据会话时显示传输 ID 和已收片数，并提示等待第 1 片。
- 恢复后继续使用相同接受规则，禁止把其他传输片段合入当前会话。
- 完成并成功触发下载或用户选择重新开始后清除会话。
- `localStorage` 配额不足时扫描可继续，但必须持续显示“无法保存恢复进度”，不能用一次性消息覆盖后消失。

## 安全边界

- QR 内容、文件名、MIME 类型和持久化数据全部视为不可信输入。
- 所有用户或 QR 来源字符串必须通过 `textContent` 或文本节点写入页面。
- 禁止把文件名、MIME、错误内容或扫描载荷插入 `innerHTML`。
- `innerHTML` 仅允许用于完全静态、代码内定义且不拼接外部值的 UI 片段。
- 文件名只用于浏览器下载属性；页面显示始终使用文本节点。
- 恢复会话加载后必须重新做结构验证，损坏或旧版会话直接清除并回到空闲状态。

## 测试设计

### 生产逻辑测试入口

`receiver.html?test=1` 暴露只读快照和明确的测试操作 API。该 API 只在测试查询参数存在时注册，供同源 `test.html` 的隐藏 iframe 调用；正常接收页面不暴露测试接口。

测试必须调用生产页面实际的 V2 解析、状态合并、持久化恢复和安全渲染逻辑，不能继续复制一套接收算法。

### 必须新增的回归测试

1. 私有文本正常、乱序、重复片段和缺片补传。
2. 文件数据片先于元数据片到达，元数据到达后已有片段仍保留。
3. 活动文件传输收到另一传输的数据片或元数据片时不切换、不污染。
4. 无元数据会话刷新恢复后可以继续接收并完成。
5. 负数、越界、非整数片号，零或变化的总片数，以及错误字段类型均被拒绝。
6. Base64 损坏、文件大小不符和 SHA-256 不符均不能启用下载。
7. 含 HTML 标签和事件属性的文件名只显示为纯文本。
8. 公有单片文本被普通 QR 解码后等于原文。
9. 公有多片文本逐片解码后均为带可读序号的明文。
10. 发送端文件 V2 分片经生产接收逻辑重组后与原始随机字节完全一致。
11. 发送端和接收端在无网络条件下不请求任何运行时资源。

### 验证门槛

- 原有适用测试和全部新增测试通过。
- 发送端、接收端首次加载无 JavaScript 错误和网络依赖错误。
- 至少执行一次随机二进制文件的生产 V2 字节级往返。
- 使用普通二维码解码路径验证公有文本单片和多片载荷。
- 工作区只包含本次明确修改的文件，不覆盖用户已有未跟踪内容。

## 非目标

- 不兼容旧版私有文本或文件分片。
- 不让第三方扫描器自动重组私有文本或文件。
- 不实现 RaptorQ、并行四 QR、原生 App 或 Worker/Canvas 性能流水线。
- 不改变当前视觉设计，也不重构与本修复无关的嵌入式 QR 库。

## 成功标准

- 公有文本可由普通二维码扫描器逐片读取。
- 私有文本和文件支持乱序、去重、恢复、缺片查看和指定编号补传。
- 任意合法片段都可以作为接收起点，不因元数据晚到丢失进度。
- 不同传输不会静默混合或导致 UI、内存和持久化状态分叉。
- 文件仅在长度和 SHA-256 均正确时允许下载。
- 恶意文件名无法生成 HTML 节点或执行脚本。
- `sender.html` 与 `receiver.html` 各自保持完整自包含。

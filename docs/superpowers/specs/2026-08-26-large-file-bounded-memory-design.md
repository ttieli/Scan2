# 大文件有界内存传输设计

## 目标

确保低端电脑和手机处理 5MiB 以内文件时页面保持响应、能够完成传输并支持恢复；5–20MiB 文件进入明确的超长传输模式；超过 20MiB 的文件在读取和哈希前直接拒绝，保证不会因为尝试处理超大文件而卡死浏览器。

本次保持 V2 QR 线上协议字段不变，不追求缩短物理扫描时间。文件越大，传输仍可能持续数小时。

## 根因

### 发送端

- 当前把完整文件读入内存并生成完整 Base64。
- `buildV2Fragments` 为每一片创建对象和字符串数组。
- `generatePrivateQRCodes` 同步为全部片段创建 DOM、Canvas 和 QR。
- `qrCache` 随浏览页数无限增长。

H 纠错下，5MiB 文件会产生约 134,434 片。仅 200×200 Canvas 的理论像素内存就约 20GB，因此真正的卡死点是全量二维码渲染，而不是 SHA-256 或分片计算。

### 接收端

- 每接收一片都通过 `Object.keys(activeTransfer.fragments)` 全量计数，累计复杂度为 O(n²)。
- 每片都将全部累计数据 `JSON.stringify` 后重写 LocalStorage，产生 O(n²) CPU/复制开销并最终超过存储配额。
- 进度图为每个片段创建一个 DOM 节点；5MiB 可生成 13 万个以上节点。
- 缺片列表可能一次拼接数十万个编号。

## 文件大小策略

使用二进制 MiB：`1 MiB = 1024 × 1024 bytes`。

| 文件大小 | 行为 |
|---|---|
| `0–5MiB` | 正常支持，保留用户选择的 L/M/Q/H 纠错级别 |
| `>5MiB–20MiB` | 超长模式；强制 L 纠错，显示准确片数/预计时间并要求用户确认 |
| `>20MiB` | 在 `FileReader`、SHA-256 和 Base64 前直接拒绝，提示压缩或拆分 |

20MiB 上限同时在文件选择、拖放、生成按钮和测试 API 边界验证，不能只依赖 UI 提示。

## 发送端架构

### 惰性片段源

文件传输不再返回完整 `fragments[]`。改为 `V2FragmentSource`：

```js
{
  kind: 'f',
  id: '16hex',
  total: 134434,
  metadata: { ... },
  getFragment(index): V2Fragment,
  getPayload(index): string
}
```

源对象仅保存文件元数据、完整 Base64、已计算的安全数据片长度和总片数。`getFragment(index)` 根据索引即时切片和序列化。

`buildV2Fragments` 的安全片长计算改为数学迭代：根据 Base64 长度、总片数字数和最坏索引 JSON 开销确定片长，不得为候选片长反复创建完整数组。

### 分批预处理

文件读取后按以下阶段显示进度：

1. 读取文件。
2. 计算 SHA-256。
3. 分批转换 Base64。
4. 建立惰性片段源。

Base64 转换按固定、可安全拼接的三字节倍数分批，并在批次间主动让出事件循环。用户可以取消；取消后释放 ArrayBuffer、Base64 和片段源引用。

20MiB 内允许保留原始字节和 Base64，但不得同时再物化全部片段对象/JSON/Canvas。目标峰值内存低于 128MiB。

### 有界渲染

- 网格模式改成分页，每页最多 12 张 QR。
- 页面切换时销毁上一页 Canvas 和 DOM。
- 循环和单张模式只渲染当前片。
- 二维码缓存使用 LRU，最多保留 8 张 PNG/Data URL。
- `qrCodes.length`、索引跳转、循环范围、指定编号补传统一改为通过片段源访问。
- 不允许任何代码路径按总片数创建 DOM 或 Canvas。

### 大文件确认

生成前显示：文件大小、实际纠错级别、总片数、按当前循环速度估算的理论时长。5–20MiB 文件必须确认后才继续，且明确说明可能持续数小时。

## 接收端架构

### 常数时间接收状态

活动文件状态只在内存保存：

- 传输 ID、元数据、总片数。
- `receivedCount` 数字。
- `Uint8Array` 位图，1 bit 表示一个片段是否收到。
- 固定数量的聚合进度桶。

新片到达时通过位图 O(1) 判断重复并更新计数，禁止在扫描热路径调用 `Object.keys()`、排序或遍历全部片段。

### IndexedDB 片段存储

文件片段使用自包含页面内的 IndexedDB：

- 数据库：`qr-transfer-v2`。
- `sessions` 存储会话头、元数据、位图和计数。
- `fragments` 以 `[transferId, index]` 为键保存数据片。
- 扫描处理通过串行异步队列写入；队列超过安全水位时跳过当前视频帧，让重复播放自然补扫。
- 位图和会话头按片数/时间节流保存，不每片重写整个会话。
- IndexedDB 不可用或写入失败时停止文件接收并给出明确错误，不退回高风险 LocalStorage 全量存储。

文本小传输可以继续使用现有内存/LocalStorage 路径。

### 聚合进度图

- 总片数不超过 200 时保持逐片格子。
- 超过 200 时固定显示最多 200 个进度桶。
- 每个桶表示连续编号范围，以接收比例着色。
- 每扫一片只更新对应桶和统计文本，不重建地图、不遍历全部片段。

### 缺片范围

大传输的缺片结果使用范围压缩，例如 `1-120, 145, 201-260`。发送端编号解析器同时支持单个编号和闭区间，避免创建或复制数十万字符。

缺片计算按批次执行并可取消，不阻塞摄像头预览。

### 恢复与完成

- 页面恢复时从 `sessions` 加载位图和计数，不立即加载全部片段。
- 继续扫描时按需写入 IndexedDB。
- 完成后按索引游标分批读取片段、组装 Base64、解码字节并计算 SHA-256，持续显示进度并让出事件循环。
- 最终 Blob/File 创建成功后继续保留 IndexedDB 会话，直到用户明确“重新扫描”。
- 用户清除会话时删除对应 transferId 的 session 和 fragments 记录。

## 兼容性

- QR 载荷仍是 V2 `{v,k,x,i,t,d,m}`，现有新版本发送端/接收端互通语义不变。
- 仅发送端内部由数组改为惰性源，接收端内部由对象/LocalStorage 改为位图/IndexedDB。
- IndexedDB 是 iOS Safari、Android Chromium 和主流桌面浏览器的基础能力。
- `sender.html` 必须继续作为单文件完整自包含产物：二维码库、惰性片段、分页、LRU、进度和取消逻辑全部内嵌，不新增 `<script src>`、CDN、动态 `import()`、`fetch()`、外部 Worker、服务器或构建产物依赖。
- `receiver.html` 同样保持单 HTML 自包含。

## 性能门槛

以 5MiB H 纠错和 20MiB L 纠错作为最坏结构测试：

- 片段源创建不得生成完整片段数组。
- DOM/Canvas 数量始终不超过当前网格页 12 张或当前全屏 1 张。
- QR 图像缓存不得超过 8 项。
- 聚合进度 DOM 不得超过 200 个桶加固定标题节点。
- 接收热路径不得调用 `Object.keys(activeTransfer.fragments)` 或全量 LocalStorage 序列化。
- 单个同步任务目标不超过 50ms；长处理必须分批让出事件循环。
- 5MiB 预处理在低端设备上必须有可见进度和取消入口，页面输入/按钮仍可响应。
- 20MiB 以上文件必须在读取前拒绝。

## 测试

### 发送端

1. 5MiB H 和 20MiB L 返回惰性源，片数正确，`materializedFragmentCount` 为 0。
2. 20MiB + 1 byte 在读取/哈希前拒绝。
3. 5–20MiB 自动进入 L 模式并要求确认。
4. 首片、中间片、末片 QR 经过 QRCode.js → jsQR 后载荷一致。
5. 网格翻页后 DOM/Canvas 不超过 12。
6. 循环 1000 次后缓存不超过 8。
7. 取消预处理后不进入可播放状态。

### 接收端

1. 位图重复检测和 `receivedCount` 为 O(1) 语义。
2. 13 万片聚合地图不超过 200 个桶。
3. IndexedDB 写入、重复片、刷新恢复、清除会话。
4. 队列高水位时跳帧而不是无限堆积。
5. 缺片范围压缩与发送端范围解析互通。
6. 分批完成验证与原始随机字节一致。
7. IndexedDB 失败时停止接收且不写 LocalStorage 大对象。

### 回归

- 现有 20 项协议、标准 QR、尺寸、文件操作和安全测试继续通过。
- 浏览器套件连续运行两次结果一致，无当前页面控制台错误。
- 生产页面自包含和危险渲染扫描继续通过。
- 独立复制 `sender.html` 后，在断网和没有相邻项目文件的情况下仍能选择文件、预处理、分页显示、循环和补传。

## 非目标

- 不保证超过 20MiB 的文件传输。
- 不缩短物理扫描时间。
- 不在本轮引入 RaptorQ、喷泉码、多 QR 并行、Web Worker 或新的线上协议版本。
- 不承诺浏览器或设备在数小时扫描期间不会被操作系统休眠、杀后台或耗尽电量。

## 成功标准

- 5MiB 文件在低端电脑和手机上不会因全量 DOM、Canvas、LocalStorage 或 O(n²) 计数卡死。
- 5–20MiB 文件可进入超长模式且页面保持有界内存和可响应。
- 超过 20MiB 文件立即、安全、可解释地拒绝。
- 发送端、接收端的 DOM、缓存和扫描热路径开销不随总片数线性膨胀。
- 传输协议、SHA-256、补传、恢复和文件操作功能保持正确。
